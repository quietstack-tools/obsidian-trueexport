# Contributing to TrueExport

## Bug reports and feature requests — yes please

These are genuinely the most valuable thing you can send me. Open an issue.

For bug reports, the single most useful thing you can include is **the note that
broke**, or a minimal version of it. Export problems are almost always about one
specific construct, and a reproduction saves hours of guessing.

Security issues: please email **support@quietstack.tools** rather than opening a public
issue. I won't threaten you for reporting one — see clause 4 of
[COMMITMENTS.md](COMMITMENTS.md).

## Code contributions — not at this stage

**I'm not accepting pull requests right now.** PRs will be closed unmerged. This
isn't about the quality of your work, and I'd rather tell you before you spend
an evening on something.

The reason is boring and legal. TrueExport is a commercial product. A
contributor keeps the copyright in their contribution, so merging a patch
without a contributor agreement in place would leave me distributing code I
don't have the rights to re-license — which constrains the project permanently,
for a small patch. Setting up and administering a contributor licence agreement
isn't proportionate for a project this size yet.

There's a second reason worth being upfront about: if you send me a patch and I
later build the same feature myself, that's an awkward conversation neither of
us wants. A clear "no PRs" policy protects both of us from it.

## What you can do instead

- **Open an issue** describing the change. If it's a good idea I'll build it and
  credit you in the release notes.
- **Fork it.** PolyForm Shield expressly permits making changes and new works,
  and distributing them, for any purpose except providing a competing product.
  Your fork is yours.
- **Ask** if you're unsure whether something counts as a competing product —
  **support@quietstack.tools**. I'd much rather answer a question than have someone not
  build something useful.

If this policy changes, it'll be announced here and in the CHANGELOG.
